# 开发与发布工作流

## 当前阶段

当前只有本地 main，未配置远程，正在开源准备。用户明确要求后才提交、推送、创建 PR、合并、打 tag、部署或重写历史。日常实施先形成可审查的 diff 与验证结果。

开源准备期间，经维护者授权可创建本地里程碑提交，用于保存阶段性成果。这些提交属于内部工作历史；首次公开前按既定安排整理为单个干净 init commit，里程碑提交不进入正式开源后的 Git 历史。提交范围仍遵守私有目录与多媒体的跟踪边界。

远程启用后的分支模型保持轻量：主线开发直接在 main 上进行；是否开分支由维护者逐案决定——仅大规模、高风险或长周期改动从 main 分出短分支并以 PR 合回，分支只承载单一意图、合后即删，不设 develop／release／hotfix 常设分支。远程分支保护规则随首次公开时确认。

## 按风险交付

| 变更 | 最小检查 | 评审 |
|---|---|---|
| 文档与小型维护 | 源码检查、链接与过时术语 | 本地可审查结果；公开 PR 按范围审查 |
| 普通内容修复 | 源码检查、DLL 编译、相关游戏行为 | 小范围 PR 审查 |
| 核心机制、钩子、持久化、跨模块重构 | 完整构建、对应边界与负向场景、真实试玩 | 未参与实现的独立 CR |
| 发布候选 | 完整环境与发行物验收、兼容矩阵、回退材料 | 独立 CR 与维护者接受 |

大型跨领域工作先在私有工作区写目标、边界、失败模式和拆分方案。评审结论采用 Blocking、Should-fix、Nits、Verified claims；Blocking 合入前修复，Should-fix 修复或记录延后理由。尚未部署 Bot Review，不把其他仓库的机器人机制列为当前门禁。

## 提交与文档

遵循 Conventional Commits，提交信息一律使用英文，主题与正文分别经 `-m` 提交。修改拥有该事实的文档，交付前搜索旧版本、命令、路径和机制术语。日常 CHANGELOG 草稿可存于私有目录并附在 PR 描述，发布前按新增／变更／移除／修复等类别汇总；不记录提交哈希流水账。

## 发布与首次公开

1. 冻结清单版本、候选提交、游戏和 RitsuLib 对应关系、CHANGELOG 及发行范围。
2. 完成源码检查、编译、完整素材和 PCK 验证；在真实游戏验证安装、角色、核心机制、事件、世界线与必要读档／原版联动。记录未完成项，不能用 CI 替代试玩。
3. 按清单版本生成包，核对包内清单、游戏目标、内容、校验值与发布说明。保留上一验收包和存档备份说明。
4. 首次公开前，核对已采用的 MIT 许可范围、原创文案贡献与素材来源、发行包内许可文件；维护者确认公开文件树与媒体分发范围。local_dev 整体忽略，公开内容按[文档边界](documentation.md)提取。私有备份保留原工作历史，再按明确授权把历史整理为单个干净 init commit。
5. 收到明确指令后配置远程与首次推送；后续发布在已接受 main 上打 tag。tag、Release 和发行包版本一致。
6. 发布后在 main 上更新当前状态、下一开发目标与已发布草稿。

当前不自动重写历史、创建远程、上传素材或宣告正式版。
