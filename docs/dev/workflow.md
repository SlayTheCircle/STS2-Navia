# 开发与发布工作流

## 当前阶段

仓库已公开，主线开发在 main 上进行。用户明确要求后才提交、推送、创建 PR、合并、打 tag、部署或重写历史。日常实施先形成可审查的 diff 与验证结果。

远程启用后的分支模型保持轻量：主线开发直接在 main 上进行；是否开分支由维护者逐案决定——仅大规模、高风险或长周期改动从 main 分出短分支并以 PR 合回，分支只承载单一意图、合后即删，不设 develop／release／hotfix 常设分支。远程分支保护规则按维护者决定配置。

## 按风险交付

| 变更 | 最小检查 | 评审 |
|---|---|---|
| 文档与小型维护 | 源码检查、链接与过时术语 | 本地可审查结果；公开 PR 按范围审查 |
| 普通内容修复 | 源码检查、DLL 编译、相关游戏行为 | 小范围 PR 审查 |
| 核心机制、钩子、持久化、跨模块重构 | 完整构建、对应边界与负向场景、真实试玩 | 未参与实现的独立 CR |
| 发布候选 | 完整环境与发行物验收、兼容矩阵、回退材料 | 独立 CR 与维护者接受 |

大型跨领域工作先在私有工作区写目标、边界、失败模式和拆分方案。评审结论采用 Blocking、Should-fix、Nits、Verified claims；Blocking 合入前修复，Should-fix 修复或记录延后理由。尚未部署 Bot Review，不把其他仓库的机器人机制列为当前门禁。

## 提交与文档

遵循 Conventional Commits，提交信息一律使用英文，主题与正文分别经 `-m` 提交。修改拥有该事实的文档，交付前搜索旧版本、命令、路径和机制术语。日常 CHANGELOG 草稿可存于私有目录并附在 PR 描述，发布前按新增／变更／移除／修复等类别汇总；不记录提交哈希流水账。

## 发布流程

1. 冻结清单版本、候选提交、游戏和 RitsuLib 对应关系、CHANGELOG 段落及发行范围。
2. 完成源码检查、编译、完整素材和 PCK 验证；在真实游戏验证安装、角色、核心机制、事件、世界线与必要读档／原版联动。记录未完成项，不能用 CI 替代试玩。
3. 在已接受的 main 上打 `v*` tag 并推送：Release 工作流在托管 runner 检出私有构建输入（circle-refs 编译参考与美术母版仓）完成完整构建，校验 tag 与清单版本一致，从 [CHANGELOG](../../CHANGELOG.md) 提取发行说明，创建草稿 Release。fork PR 拿不到 secret，不会触发构建。
4. 维护者下载草稿 Release 的发行物试玩验收，保留上一验收包与存档备份说明；通过后手动发布。tag、Release 和发行包版本一致。
5. 发布后在 main 上更新当前状态、下一开发目标与 CHANGELOG。

当前不自动重写历史，公开仓不收纳美术母版与游戏引用；正式版宣告由维护者验收草稿后手动完成。
