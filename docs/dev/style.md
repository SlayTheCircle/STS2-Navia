# 工程规范

## 职责与依赖

模块化与解耦是本项目的明确工程偏好，也是新增实现与重构的评审要求。内容类放入最窄的领域模块；模块拥有清晰职责、状态和不变量，通过范围明确的 API 协作。按职责和变更原因评估结构，行数与文件数只作审查线索。

ModEntry 负责归属、关键词、角色资源和补丁的组合接线；卡牌、力量、遗物、事件与世界线分别拥有其机制。领域逻辑落在对应模块，不把新逻辑默认堆入入口或泛化 helper。避免循环依赖、跨模块读取内部可变状态和靠隐含调用顺序维持正确性；副作用与依赖在接口和调用位置表达清楚。

复用现有 Base 家族和 RitsuLib 扩展点。原版硬编码表、钩子和模型语义先查同版本实现；自建状态或补丁前确认已有通道。新增 HarmonyPatch 必须确认 PatchAll 已执行。

## 禁止上帝文件、上帝类与上帝函数

不得新增或继续扩张集中承担多个独立职责的上帝文件、上帝类或上帝函数。以下情况需要拆分职责：

- 一个文件汇集多个可独立维护的模块、策略或业务流程。
- 一个类同时承担内容规则、状态管理、资源访问、持久化或展示等多种独立角色，并因此拥有多个变更原因。
- 一个函数混合多个独立流程、不同抽象层次或大量模式分支，修改局部行为必须理解整个函数。

按独立职责、状态归属或稳定策略提取模块、类和函数。协调入口可顺序调用这些模块，复杂判断与领域状态由其拥有者维护。拆出的单元应有明确名称、输入、输出与副作用；不能只是把同一大块逻辑挪进一个 Utils、Manager 或另一份巨型文件。

函数围绕一个可命名的任务组织，同一层次描述步骤；独立子任务、边界转换和重复规则抽成具名单元。抽象用于隔离真实变化与依赖，不为每个短表达式创建包装或无消费者的接口。重构时说明拆分后的职责与调用关系，并保持模型身份和现有行为。

## 目录模块化与文件收纳

单一文件夹内平铺文件明显增多时，优先考虑建立有意义的子目录，再决定新增文件落点。按领域职责、机制家族或共同变更关系收纳；同时适用于源码、脚本和文档。不等到查找与审查已经困难才处理目录增长。

目录名说明内容归属，避免 Misc、Other 或纯粹按数量分组。跨多个机制的卡牌选定稳定的主归属，不复制文件；共同规则放在机制模块。目录深度服务于导航，不能每个文件建立一层目录或为凑规模机械拆分。

移动文件时核对命名空间、注册发现、资源与本地化 ID、项目包含规则、脚本扫描范围和文档引用。目录调整不应顺带改变内容身份或存档语义。实际目录布局及当前扫描限制见[架构](architecture.md)。

## 结构评审

新增或修改实现时检查：职责能否用一句话说明？状态与不变量是否有明确拥有者？是否引入跨模块内部耦合？是否扩大已有上帝文件／类／函数？目标目录是否需要子模块收纳？

发现上述结构问题时，应在当前变更的合理范围内拆分；已有问题超出范围时明确记录后续重构，不能把既有平铺或集中实现当成新代码继续扩张的依据。

## 内容契约

- 每类内容使用对应 Base；隐藏 Power 可直接继承 PowerModel。
- 同一模型只走一个注册来源；自己的类型列表池通过属性聚合，不重复手工注册。
- 复合 ID、类名与本地化键保持一致；双语键覆盖所有现行表。
- 打击类卡显式声明 CardTag.Strike；原版联动以标签判定。
- 伤害与格挡预览、升级变量、关键词变更和支援钩子遵循卡牌手册。
- 可见 Power 同时供小图与大图；遗物和药水供齐各资源槽。

## 状态、副作用与错误

装填变化经 LoadPower.Gain，礼炮动作经 Salvo.Fire；共享不变量由机制拥有者维护。区分主卡组、战斗克隆、单卡实例和持续 Power 的作用域。持久化需求先明确读档、升级回放与战斗清理语义。

战斗结束、空牌堆、取消选牌和可空返回是正常边界，分别处理。未知异常不静默吞掉；构建、导入、复制和包验证失败必须返回失败。持续关键词由解析钩子表达，一次性升级变化用 AddKeyword／RemoveKeyword。

## 注释与环境

注释说明约束、版本依据和容易误改的原因。完成改动后清理当前范围内的死代码与过时说明。本机路径只出现在私有配置；脚本从开发环境模块读取，外部资源只读参照。

写入后回读文件及 diff。构建输出完整接收，避免提前退出的管道截断产物脚本。文本使用 UTF-8 / LF；测试与验证遵循 [验证纪律](testing.md)。
